# Pi 接口兼容性验证

日期：2026-09-09。验证基线：本机已安装的 Pi **0.84.1**，Node.js **24.15.0**。

## 结论

已完成本轮接口验证：**17 项协议断言全部通过**，包括对“不支持的能力”的负向断言。因此不能将 17 项通过理解为 Pi 原生具备所有产品功能。

一期的聊天、并行会话、历史恢复、模型切换、图片传递、命令发现和基础交互，可通过 `pi --mode rpc` 实现，无须修改 Pi 或重写 Agent。必须处理以下边界：

1. **应用持有尚未发送的消息队列。** 0.84.1 的 RPC 没有 `clear_queue`，也没有单条消息的原子“队列转插入”接口。待发送消息先保留在客户端，正常在当前执行完全结束后提交；点击“立即插入”时从客户端队列移除并发送 `steer`。已提交给 Pi 的消息不能再宣称可随时撤回。实测此路径按预期各交付一次；跨进程崩溃时的投递确认和持久化仍属于产品实现工作。
2. **图片与普通文件走不同通路。** RPC 的 `images` 支持图片；不存在统一的 `files` 附件字段。普通文件由应用保存到管理目录，向 Agent 提供准确路径，由 Agent 的文件工具/Skills 处理。真实内置 `read` 已成功读取测试文件。不能据此承诺 Pi 原生理解任意 PDF、Word、视频等格式。
3. **复用扩展不等于复用终端界面。** `select`、`confirm`、`input`、`editor` 的 RPC 往返均已实测；`custom()` 在 RPC 返回 `undefined`，不会执行终端 UI 构造函数。`editor` 只需承接多行文本问题，不代表要做文件编辑器。不能宣称所有现有扩展都兼容，具体扩展若依赖 TUI 必须单独适配或明确不支持。
4. **通知必须基于真实执行状态。** `prompt.success` 只表示已接收；`agent_end` 后还可能重试；`agent_settled` 表示本次执行不会自动继续，并不等于业务成功。需结合消息的 `stopReason` 和错误区分完成、失败、停止。等待回答只依据明确交互请求，不能通过猜测普通回复是否是问句来判断。
5. **历史管理和展示是应用职责。** Pi 提供消息、会话条目、恢复和重命名；0.84.1 的 RPC 没有完整的全局历史搜索、置顶、删除管理接口。应用只索引自己创建的会话，维护自己的展示元数据；不能接管终端正在使用的会话文件。文件链接也没有统一的结构化产物事件保证，可从回复中的有效本地链接提供系统打开入口，不应将工具日志全部暴露给用户。

## 验证方式

使用真实本机 Pi CLI 子进程，通过 stdin/stdout 发送和接收 JSONL。模型端采用只监听 `127.0.0.1` 的确定性测试服务，模拟文本流、工具调用、耗时响应、临时错误和最终错误。Agent 循环、工具执行、资源加载、会话落盘、重启恢复和交互协议均由真实 Pi 执行。

测试模型服务仅是测试夹具，不是产品对接模型的方案。应用的产品边界仍是“应用 → Agent → 模型”。

测试使用工作目录下独立的 Pi 配置、测试模型、Skills、模板、扩展和会话路径；未修改用户现有 Pi 配置，未读取真实凭证或调用真实模型服务。最终测试禁用自动扩展/Skill/模板发现，并明确加载夹具；Pi 自带的 `llama` 命令仍会出现。

## 实测矩阵

| 编号 | 验证项 | 结果及证据 |
|---|---|---|
| 1 | 启动、模型发现与切换 | 无终端 UI 即可响应 RPC；返回两个已配置测试模型，切换成功 |
| 2 | 流式回复、持久化、会话目录 | 收到 `message_update` 和 `agent_settled`；会话文件位于指定目录 |
| 3 | 工具执行状态 | 收到 `tool_execution_start/update/end`，可只转换为简短状态 |
| 4 | 排队与插入时序 | 执行工具期间发送 follow-up 和 steer；工具结束后先消费 steer，再处理 follow-up |
| 5 | `clear_queue` 可用性 | 0.84.1 返回 `Unknown command: clear_queue`，确认不支持 |
| 6 | 客户端队列转插入 | 客户端暂存两条消息；一条 steer，另一条在 settled 后提交；均恰好出现一次 |
| 7 | 图片传递 | `images` 经 Pi 转换后作为图片 data URL 到达测试服务 |
| 8 | 普通文件字段 | 额外传入的 `files` 被忽略，不会自动成为模型附件 |
| 9 | 普通文件路径交接 | 真实内置 `read` 读取测试文件，其内容进入后续模型请求 |
| 10 | `/` 命令、Skill、模板 | 列表包含三类资源；模板参数展开、Skill 内容加载均成功 |
| 11 | 确认与 TUI 降级 | confirm 请求/响应成功；custom 返回 undefined |
| 12 | 选择、单行输入、多行输入 | select/input/editor 三类请求均能通过 RPC 完成 |
| 13 | 多会话并行 | 两个 Pi 进程同时处理请求；各自历史不包含另一会话的测试消息 |
| 14 | 重命名、重启续聊、停止 | 会话 ID、名称和条目在重启后保留；可继续发送；abort 后空闲 |
| 15 | 未配置 Agent | 无可用模型时仍能响应状态查询；发送返回缺少凭证错误，可用于引导 |
| 16 | 重试与完成通知 | 503 触发自动重试，重试结束后只产生一次 settled，避免提前通知完成 |
| 17 | 接收成功但执行失败 | prompt 接收成功，后续消息 stopReason=error；能区分协议接收与执行结果 |

## 静态核查补充

本机安装包的 `dist/modes/rpc/rpc-mode.js`、`rpc-types.d.ts`、`dist/core/agent-session.js`、`dist/core/settings-manager.js`、`dist/config.js` 和 `docs/models.md` 与真实测试相互核对。

默认配置目录仍为 `~/.pi/agent`；`--session-dir` 可以独立指定会话目录。因此正式应用可复用 Pi 的认证、模型和资源配置，同时只将自己的会话写入应用管理的路径。测试为避免改变用户配置而覆盖了配置目录；未逐个运行用户安装的扩展或真实 OAuth 流程。

本机的 `pi auth check --help` 显示支持 `--json` 和 `--no-refresh`；此轮没有对真实账号调用认证检查。模型列表非空不能证明网络、凭证有效期、余额或模型端服务可用。应用应让 Pi 报告错误并引导用户处理，不提取凭证，不承诺零请求即可验证所有服务可用性。

SDK 层存在 `clearQueue()`，但本机 RPC 未暴露它。这是 SDK 与 RPC 的接口差异，不能混用文档。后续应以已验证的版本为兼容基线，版本变化后运行契约测试；不建议假定“高于 0.84.1 的任何版本都兼容”。

## 已证实限制与未覆盖范围

接口层的主要待确认项已验证。以下不应误报为已经验证：真实模型推理/视觉质量、所有文件格式、所有第三方扩展、真实提供商 OAuth 刷新、macOS 通知和焦点行为、休眠恢复、进程异常退出后的消息投递保证、长期并发资源占用。

这些分别属于提供商/扩展专项兼容或后续产品实现与系统测试，不能由本轮本地 RPC 契约测试推出结论。特别是“agent_settled 表示业务目标已成功完成”和“任何扩展均可复用”两个假设已被明确排除。

## 复现与产物

在当前工作区执行 `node scripts/verify-pi.mjs`，要求 `pi` 和 Node.js 已在 PATH 中。脚本在 `work/pi-verification/` 写入合成夹具，在 `outputs/pi-compatibility-results.json` 写入结果；不会安装或更新 Pi。

归档产物：`docs/pi-compatibility-results.json`（逐项结果）、`scripts/verify-pi.mjs`（可复现脚本）。再次运行生成的结果位于 `outputs/`。脚本的 PASS 包括预期不支持能力的负向测试。

官方背景参考：[Pi RPC 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)、[Pi 模型配置文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/models.md)。这些链接跟踪 main，可能不同于本次验证的已安装版本；本报告结论以本机 0.84.1 实测为准。
