# 活动窗口屏幕与浮窗激活回归修复

## 原因与修复

前次为修复键盘输入而启用正常应用激活后，浮窗成为本应用的 keyWindow；原来的 CoreGraphics 筛选只接受 layer 0，忽略浮窗，错误选中了另一屏幕的主窗口。原生复现明确得到 expected=2、actual=1，重复唤起也会跳到主窗口屏幕。

现在仅当前台应用为自身时以 AppKit keyWindow 为准；其他应用继续通过前台进程的窗口几何信息选择屏幕。每次唤起只获取一次目标屏幕，避免激活过程中重新读取变成主窗口所在屏幕。

跨应用验收另外发现，AppKit 激活完成时可能恢复主窗口焦点。显式唤起会记录待完成意图和原始屏幕，在 ApplicationDidBecomeActive 后恢复浮窗位置与输入焦点。隐藏浮窗或主动打开主窗口会取消该意图，普通后台事件不会主动夺取焦点。

## 验证范围

- 修复前的不同屏幕主窗口/浮窗回归能够失败，修复后通过。
- 3 块物理显示器、28 项原生检查：跨屏定位、重复收起、从独立前台应用唤起后的屏幕与焦点、主窗口与浮窗 AppKit 输入、隐藏、Dock 重开、全屏。
- 独立前台应用使用临时目录中的独立可执行文件，避免共享产品 bundle 身份；等待前台窗口稳定后触发唤起，防止测试应用启动激活与模拟快捷键竞争。退出后仅终止该测试进程，不访问用户会话。
- 键盘检查等待 WKWebView 真正可接受输入后发送 AppKit keyDown，验证 React 草稿持久化；该检查不是物理快捷键或像素遮挡测试。
- `go test -race .` 通过；生产应用构建通过。

早期只检查几何位置的通过结果未用于最终验收。最终报告保留跨应用“位置正确且浮窗拥有键盘焦点”的断言。

完整原生套件连续两轮均为 28/28 通过。
