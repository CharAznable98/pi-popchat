# 浮窗键盘输入修复

2026-09-09。实际桌面复现：浮窗的消息输入框在可访问性树中已聚焦，但按 p 没有文字，点击输入框再按 p 仍无变化；主窗口同一路径可输入 p。前端通过设置 value 能更新浮窗草稿，隔离原生探针直接将 AppKit keyDown 送入浮窗也能更新草稿，排除 React 输入或草稿覆盖，问题在非激活浮窗的系统焦点/键盘路由。

生产修复只有窗口配置变更：继续使用 Floating NSPanel，但不使用 NonActivating。用户显式唤起时，Wails 正常激活应用并将浮窗设为 key window。显示器选择仍发生在激活前；置顶、外部点击保持、Esc 隐藏与后台任务解耦仍沿用原实现。通知本身不调用此唤起逻辑。

同路径实际复验：点击输入框后按 p 能追加文字；Esc 收起后重新打开浮窗，不再次点击即按 q，也能写入。诊断字符均未发送，已清理。这里是桌面自动化按键，不声称完整物理输入法候选交互验证。

新增两个 AppKit keyDown → React → 持久化草稿检查，以及应用未激活时显式唤起应同时激活应用和聚焦浮窗的检查。后者实际激活 Finder 创建前置条件（不读取 Finder 内容）；仅调用 NSApp.deactivate 不会可靠改变应用活跃状态，不能用作该场景的准备步骤。

最终原生检查 22/22 通过，包括三个显示器定位、跨屏移动、同屏隐藏、转主窗口、关闭/Dock、真实本应用全屏进出及新增输入检查。Go 原生测试 race 通过，生产构建与签名校验通过。证据：docs/validation/panel-input-native.json。

此前仅验证“浮窗可见且已聚焦”不足以证明用户能输入；内部注入按键也不能单独证明系统键盘焦点路由。因此保留桌面自动化的同路径复现和后台激活检查，不将不同层次的证据互相替代。
